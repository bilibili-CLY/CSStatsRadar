# Project interaction invariants

These rules are product requirements. Preserve them in every UI, rendering, and refactor change.

## Radar rendering

- The outer radar ring is a reference scale, not a clipping boundary. Metric values above the configured maximum must visibly extend beyond the outer ring so exceptional player performance remains obvious.
- Never apply a fixed normalized-value cap to radar vertices. Constrain only at the composition's natural safe boundary so the rendered point and its label remain visible.
- Radar label layout must measure the metric name, value, and optional `BEST` marker against per-axis safe regions. Extreme values may use compact notation, but these labels must remain wholly visible and must not overlap vertices or one another. When the radar sub-canvas sits fully inside the Data Panel, the safe regions are clipped to the panel rectangle (`labelRegion` / `showcaseRadarLabelRegion`) so no label — notably `KPR` above the top vertex — can escape the panel. The measured label box reports its top edge as a negative offset from the center line, so the upper safe distance must subtract `footprint.top`; adding it pushes the label above the panel and clips it off-canvas.
- By default, radar metric labels sit immediately outside the outer ring. Only the label whose corresponding vertex extends outward may move farther out, and it must stop at its measured safe boundary.
- Radar polygons, point markers, the six metric names, their values, `BEST` markers, and the Rating 3.0 Swing track must not overlap. Reserve separate label and Swing regions when calculating geometry.
- Point markers at radar polygon vertices are deleted for a cleaner look. Every data polygon is drawn fill-first, then a three-layer outer glow (widening blurred strokes, outermost 4.2× width at 16% alpha), then its crisp outline; the innermost glow layer is the AGENTS.md reference stroke of 2.2× width at 40% alpha, so the fill never erases half the halo. When `ctx.filter` is unavailable (some workers) the glow degrades to three stacked alpha strokes without blur. Interior fill: single-player radars 0.27, focused multi-player polygon 0.24, other live polygons 0.105, and the red queue-average baseline is never filled.
- `BEST` is rendered as one integrated gold block, never a separate badge: the metric value is enlarged by `BEST_VALUE_FONT_SCALE` (1.45×, multiplied on top of the stage-3 reference `RADAR_VALUE_FONT_SCALE` = 1.3×), the value and the lowercase word `best` (2/3 of the value size, sitting at the value's bottom-left) share the same display font — the bundled `Playfair Display` italic 900 (`frontend/public/fonts/PlayfairDisplay-Italic-VF.ttf`, SIL OFL, self-hosted; never fetched at runtime) — and its glow must follow the glyph outlines: the value and `best` are painted with blurred text shadows (`RADAR_BEST_GLOW_RADIUS` = 0.7× the BEST value size is a shadow-blur multiplier, never a circular radial gradient or a round halo). The value is drawn as a cream→gold vertical gradient with a dark-gold outer stroke and a light inner stroke. BEST does not change the metric-name size, and its measured footprint (including the BEST radial push of 1.3×) drives both the label safe distance and the vertex clearance. During player transitions, BEST styling is blended per metric through `bestAmounts` (0–1 values from `showcaseBestAmounts`): the outgoing player's BEST metrics fade toward the normal value style while the incoming player's fade in (the value is cross-painted in both fonts), so a BEST→normal handoff never hard-snaps before the color/value interpolation.
- In showcase exports, `Rating 3.0 本地近似 · 非 HLTV 官方` belongs at the bottom-left of the complete composition, not inside the movable radar sub-canvas.
- Rating 3.0 `Multi-Kill` is the multi-kill round probability (rounds with ≥2 kills ÷ total rounds), shown as a percentage with the outer ring = 20%. It is not the multiImpact sub-score; do not reintroduce the old value/max (2) during refactors.
- Rating 3.0 showcase radars use center-floor values (which map to the radar center; lower values remain at the center), persisted in `showcase.radar_floor` and editable in Settings, defaulting to KPR 0.42, Surviving 15.7%, ADR 47.5, KAST 54.5%, Multi-Kill 7%, and Rating 0.55. This applies only to the Rating 3.0 showcase renderer, never Rating 2.0. The renderer merges user overrides over the fixed defaults, so an empty/legacy `radar_floor` still yields the defaults.

## Desktop shell & embedded server (Tauri + sidecar)

- The shipped desktop product is a **Tauri 2 shell + .NET sidecar**. `frontend/src-tauri/` (`productName`/bundle product `CSStatsRadar`, identifier `com.csstatsradar.app`, NSIS `currentUser` install, 1440×900 window with a 1180×720 minimum) spawns the Kestrel sidecar **`CSStatsRadar.Server`** (`src/Radar.Server`, `<AssemblyName>CSStatsRadar.Server</AssemblyName>`) on the default loopback port **19871** (`CS_RADAR_PORT`). Packaging: `npm run stage:resources` → `dotnet publish src/Radar.Server -c Release -r win-x64 --self-contained` plus a verified FFmpeg binary into `frontend/src-tauri/staged/`, bundled via `bundle.resources: {"staged/*": ""}`. `npm run desktop:dev` / `desktop:build` wrap `tauri dev` / `tauri build` with `frontend/scripts/with-sidecar-env.mjs` (sets `VITE_CS_RADAR_URL=http://127.0.0.1:19871`). The version has a single source of truth = `frontend/src-tauri/Cargo.toml`, gated by `npm run stamp:versions` against `frontend/package.json` and `Radar.Server.csproj`.
- Do not reintroduce **Photino**. Tauri uses WebView2 on Windows by design; the old browser-mode host `src/Radar.App` (embedded `BridgeServer` + opens the system default browser + heartbeat lifecycle) still builds and is retained only as a legacy/fallback path. Keep its CSRF, heartbeat, and fatal-error-dialog hardening intact, but new desktop work (packaging, startup, shutdown, versioning) targets the Tauri shell.
- Both hosts must keep the loopback-only, no-elevation rule: the server binds `http://127.0.0.1:<port>` through Kestrel (never `HttpListener`/http.sys, which needs admin or a URL ACL and hard-crashes on normal Windows accounts). Port fallback must stay — `Radar.Server.ProbeLoopbackPort` walks up to 50 ports so a busy port degrades gracefully instead of aborting startup; the Tauri shell's fixed 19871 must fail loudly rather than silently attach to a drifted port.
- Both hosts must keep the CSRF/DNS-rebinding guard: reject `POST /__bridge` and `POST /__bridge-bin` unless the `Host` header is `127.0.0.1:port`/`localhost:port` and, when present, the `Origin` header matches a loopback origin or a Tauri origin (`http://tauri.localhost`, `https://tauri.localhost`, `tauri://localhost`; dev: `http://127.0.0.1:5173`, `http://localhost:5173`).
- Sidecar contract consumed by the Tauri shell (keep the shapes and the identity handshake): `GET /api/health`, `GET /api/app/runtime-state` → `{pid, instance_id, version, data_dir, recovery_required}`, `POST /api/app/prepare-exit?instance_id=` → `{instance_id, allowed, message}` (mismatched `instance_id` → 409), `POST /api/app/shutdown` → `{safe_to_exit:true}`. The shell spawns the sidecar with `CS_RADAR_INSTANCE_ID` and only trusts a `/api/app/runtime-state` whose `instance_id` echoes that value, so it never talks to an unrelated process on the port.
- Contract endpoints must answer with **fixed-length JSON** (`Content-Length`, never `Transfer-Encoding: chunked`): they go through the local `FixedJson` helper (`Results.Text(JsonSerializer.Serialize(...), "application/json; charset=utf-8", Encoding.UTF8, statusCode)`) instead of `Results.Json`, because Kestrel streams `Results.Json` as chunked. The Tauri shell's `raw_http`/`parse_http_response` (`frontend/src-tauri/src/lib.rs`) must still de-frame both `Transfer-Encoding: chunked` and `Content-Length` bodies, because a naive "split at the first `\r\n\r\n` then `serde_json::from_str`" reading of a chunked body fails JSON parsing forever and the shell reports the misleading "后端启动超时（15s 未确认身份）" dialog (the v2.3.0 startup failure). `ServerSidecarTests.ContractEndpoints_UseContentLength_NotChunked` guards this with a raw socket request shaped exactly like the shell's. The Rust parser is covered by `#[cfg(test)] mod tests` in the same file (run `cargo test` inside `frontend/src-tauri`); the shell's startup-timeout error must distinguish "another sidecar instance answers on the port" (report the observed `instance_id`) from a genuine timeout, and must include the resolved log directory path.
- The app's data/log root is resolved only through `Radar.Infrastructure.AppPaths` (`AppPaths.DataDir()`: `CS_RADAR_DATA_DIR` → `%USERPROFILE%\.csplayerstatsradar` → `%LOCALAPPDATA%\CSStatsRadar` → `<program dir>/data`): never from the process working directory and never from `AppConfig.DatabasePath`. `Program.cs` takes `dataDir`/`recovery-required.json`/`logs/backend.log` from it (a legacy `database_path` such as `E:\<name>.db` therefore no longer drags logs to a drive root; such a path only triggers a log warning, it is never silently migrated), `ConfigManager` resolves its default config/db paths and any *relative* configured db path against it (absolute paths are kept verbatim), `SteamAvatars`/`MediaFiles` use it for `player-avatars/`, `player-images/`, `player-mvp-backgrounds/`, `showcase-music/` and `logs/avatars.log`, and the Tauri shell writes `desktop.log` next to `backend.log` (`app.path().home_dir()/.csplayerstatsradar/logs`, falling back to `app_data_dir()/logs`). `ServerSidecarTests` sets `CS_RADAR_DATA_DIR` so tests never touch real user data, and `AppPathsTests` locks the resolution rules.
- Logs are cleared only through `Radar.Infrastructure.LogFiles` (`Enumerate()`/`IsLogFile()`/`Clear(logsDir?)`, surfaced as the `ClearLogs`, `LogsDir` and `OpenLogsDir` bridge methods and rendered in `SettingsView`'s 数据与辅助功能 card beside a read-only 日志目录 field): it deletes only `*.log` and rotated `*.log.<digits>` files directly inside `AppPaths.LogsDir()`, never recursing into subdirectories and never touching other files, retries a locked file a few times, and returns `LogClearResult{logs_dir, deleted_files, freed_bytes, failed}` with per-file failure reasons instead of throwing (deleting a log must never break the app). Keep this affordance — it is how a user resets or collects diagnostics after an import/avatar failure.
- Binary frame uploads go to `POST /__bridge-bin?exportId=...` with length-prefixed framing (`4B frameCount + 4B startIndex + N × (4B length + PNG)`), which is why `Limits.MaxRequestBodySize` must stay raised (512 MB). It must pass the same CSRF/Host check as `/__bridge`. The JSON/base64 `AppendVideoFrames` bridge method remains as a fallback and must not be removed.
- Lifecycle must never orphan processes: the Tauri shell is single-instance (`tauri-plugin-single-instance` focuses the existing window instead of launching a second copy), registers the child the moment it spawns so an early window close still reaps it, asks the sidecar via `prepare-exit` before closing, escalates to `taskkill /pid <pid> /f /t` only after `POST /api/app/shutdown` times out, and kills the sidecar on `RunEvent::Exit`. The legacy browser host keeps its page beacon (`Ping` every 5s), exiting when heartbeats stop for 120s (or after 90s if never loaded), or immediately on the `QuitApp` bridge call.
- Startup must surface fatal errors in a visible dialog, never a silent exit: the Tauri shell uses `tauri-plugin-dialog` `blocking_show()` (Error/Warning — e.g. sidecar startup timeout, exit blocked while a job runs); the legacy host uses a Windows `MessageBox`.
- Native file dialogs must work on Windows too (not just macOS osascript): spawn a `powershell.exe -STA` WinForms dialog via a temp `.ps1` script and read the chosen path from stdout. The dialog MUST be shown as a window owned by the current foreground window (`user32!GetForegroundWindow()` captured in `NativeDialogs` and passed as `-OwnerHwnd`; the script wraps it in an `IWin32Window` and falls back to the hidden TopMost form only when the handle is 0) — a dialog owned by nothing is spawned by the background bridge/sidecar process and Windows z-order puts it BELOW the browser/app window, which users read as "the button did nothing". A cancelled dialog returns `null`/empty, never an exception. Published executable names: the sidecar is `CSStatsRadar.Server(.exe)` (`Radar.Server.csproj`), the legacy browser host is `CSStatsRadar.exe` (`<AssemblyName>CSStatsRadar</AssemblyName>` in `Radar.App.csproj`), and the Tauri product/bundle is `CSStatsRadar`.
- Release pipeline: pushing a `v*` tag runs `.github/workflows/desktop.yml` (Tauri NSIS + sidecar + embedded FFmpeg) and publishes the installer (`CSStatsRadar_<version>_x64-setup.exe`) as the GitHub Release; its `validate` job must apt-install FFmpeg on the ubuntu runner because `LargeBridgePayloadTests.Full_VideoExport_Encode_And_Download` performs a real encode. `.github/workflows/release.yml` (legacy `Radar.App` browser-shell zip) is manual-only (`workflow_dispatch` with a `version` input) and must not listen to tags, so one tag yields exactly one Release. The shipped version lives in `frontend/package.json`, `frontend/src-tauri/Cargo.toml`, `src/Radar.Server/Radar.Server.csproj` (and the `frontend/package-lock.json` root version), gated by `npm run stamp:versions`; `frontend/src-tauri/tauri.conf.json` carries no version, and there is no committed `Cargo.lock`. `frontend/src-tauri/tauri.conf.json` must remain **strict JSON — no `//` comments and no trailing commas**: Tauri's own CLI parses it leniently (comments work locally), but `tauri-apps/tauri-action@v0` reads it with a plain `JSON.parse` and aborts the whole build with "Couldn't locate or parse tauri config", so the failure only ever shows up in CI. `frontend/package.json` must also keep the bare `"tauri": "tauri"` script: `tauri-action@v0` builds by running `npm run tauri build` by default and fails with `Missing script: "tauri"` without it (CI sets `VITE_CS_RADAR_URL` at job level, so the `desktop:build` sidecar-env wrapper is not needed there). `bundle.resources` in `tauri.conf.json` must use the **map form with directory paths** (`{"staged/server": "server", "staged/ffmpeg": "ffmpeg", "staged/release_version.txt": "release_version.txt"}`), never a `staged/*` glob: Tauri's `ResourcePaths` silently skips any directory a glob matches, so a glob bundles almost nothing (the 150 MiB sidecar+FFmpeg payload shrank to a 10 MiB installer) while the build still goes green — the CI step "Verify installer payload" (installer must stay above ~30 MiB) and the Windows-only FFmpeg size guard in `stage-tauri-resources.mjs` exist to catch exactly this. The Windows job must export the **real** FFmpeg binary (`chocolatey\lib\ffmpeg\tools\...\bin\ffmpeg.exe`) as `CS_RADAR_FFMPEG_EXE`, because `chocolatey\bin\ffmpeg.exe` is only a shim and is dead weight on a machine without chocolatey. `DesktopApp.DetectFFmpeg()` must keep the bundled candidates `<install>/ffmpeg/ffmpeg[.exe]` and `<install>/server/../ffmpeg/ffmpeg[.exe]` so the embedded binary is actually used (the sidecar itself lives in `<install>/server/`).

## Database schema

- SQLite schema must be forward-compatible with legacy databases: `CREATE TABLE IF NOT EXISTS` never adds columns to an existing table, so `Init()` must run a column migration (`PRAGMA table_info` + `ALTER TABLE ... ADD COLUMN`) for every column that was added after the initial release (`demos.file_sha256/source_path/match_time_source/note/analysis_version`, `player_match_stats.rating_3/round_swing/multi_kill/rating_algorithm/rating_3_metrics_json`). Never drop this migration when refactoring `Init()`.
- Newly added columns must be nullable or carry a `DEFAULT` so `ALTER TABLE ADD COLUMN` works on populated legacy rows.

## Showcase transitions

- Showcase preview and MP4 export are always a 1920×1080 (16:9) composition. Preview must letterbox/scale down to its available area rather than stretch; its native fullscreen mode must preserve that ratio.
- In showcase compositions, the Round Swing ±5% reference span must exactly equal the rendered radar's outer-ring diameter, never the radar sub-canvas diameter. Its track height is 225% of the original height. The Swing sub-canvas may be wider only to reserve independent overflow and endpoint-label safe space; values beyond ±5% extend from the fixed outer-ring-aligned endpoints into that overflow region. The fill has a square edge at the center line and may round only at its outer end.
- Transitions between players are mandatory in preview and exported video.
- Outside the explicit BEST entrance flow, the radar itself must never fade in or fade out. Interpolate each of the six radar vertices directly from the previous player's corresponding metric value to the next player's value, preserving continuous polygon motion.
- During normal player transitions, player name/subtitle, player image, and background image must crossfade while the radar vertices morph.
- Do not replace a normal player transition with a hard cut, a whole-radar opacity fade, or unrelated entrance/exit animation.
- Keep preview and export on the same renderer and transition timing so they cannot diverge.
- Showcase queue averages are a red solid, unfilled radar baseline plus a red Round Swing reference line; average values must use the active Rating profile and ignore missing values per metric.
- Showcase metric names, values, `BEST`, and all Round Swing text (label, value, and ±5% endpoints) use one global, explicitly entered pixel font size and bold weight; this setting never changes player title/subtitle or the watermark. Showcase player-image position and size are global: every slide shares `layout.imageX/imageY/imageScale`, and slides must not store independent image transforms.
- The optional showcase opener has four customizable stages: match info (default 6.0s duration; user-defined Text/Img elements with individual selection, red circular X deletion, position/scale dragging, smooth FadeIn entrance, and symmetric FadeOut exit within the last 800ms; supports optional fade-in-from-black opening transition within the first 800ms) → stage 1 (empty radar, Data Panel expands horizontally and vertically centered from horizontal 50% & vertical 80% to 54% width and 93% height, executing a Hermite continuous zero-pause spring oscillation locked at expandProgress 0.40, decay 2.5, cycles 5.0, ampW 0.05, ampH 0.05; once Data Panel reaches 75% of target size, the inner Radar Sub-canvas and Round Swing expand as a single entity from horizontal 50% & vertical 80% to user-configured layout positions and scales monotonically without jelly overshoot, immediately displaying their baseline average lines and persistent center zero line) → stage 2 (average stage: displays team averages first; radar average baseline adds glowing bloom effect in 0.5s featuring a razor-sharp coral-peach core line surrounded by deep crimson ambient mist without opacity dips or blinking; radar metric labels grow upward in three stepped batches separated by 0.1s [Rating/KPR → Multi-Kill/Surviving → KAST/ADR/Round Swing] with a smooth 0.5s growth duration each; all numeric values match the metric title font ["Noto Sans SC", system-ui] except for BEST; metric description and numeric value render on the same line pushed radially outward to avoid occluding radar vertices and polygons, with a centered Chinese alias tag in parentheses underneath [回合击杀, 存活率, 回合伤害, 不白给率, 回合多杀] — the alias row must be laid out wholly below the name/value row (below the lowercase `best` word for BEST metrics) so it never overlaps the metric name; Round Swing track height is increased by 50% with background fill removed; title and numeric value are centered directly below the bar on the same line [value on right] matching metric label color, with an underneath centered "(回合影响)" tag, and square-corner bar fill smoothly grows from center to the average line over the same 0.5s duration) → stage 3 (reference stage: outer-ring highlight and ±5% Swing reference display outer maximum reference scale; only stage 3 metric numeric values turn white and enlarge via RADAR_VALUE_FONT_SCALE = 1.3 to remain prominent, while numeric values at all other stages remain normal size; Round Swing title, value showing "+5%", underneath "(回合影响)" tag, and bar fill persist without disappearing or flickering; Round Swing value font size strictly matches the radar value size; the bar fill smoothly grows from team average to +5% over 0.5s, with seamless continuity at the stage 2→3 transition frame, and renders in green [#35d07f / #5efca8] when positive rather than white; in the final 400ms of stage 3, the Data Panel along with radar and swing executes a smooth complete FadeOut to 0, directly handing off to the main scene). The former stage 4 (outro) is deleted.
- In the main scene, the first player has a dedicated arrival pipeline (0~700ms Data Panel expansion directly toward the left target panel position at targetX 0.018 and Player Image gliding in from the right edge, settling at 700ms; 700~1100ms Subtitle growing size from 0 to target directly beneath the avatar's vertical center after avatar settles; 1100~1700ms Title entering with cyberpunk Text Scramble decoding after Subtitle settles; 700~1200ms radar/swing entrance from below vertical center with size 0->target hiding labels and values; 1200~1700ms metric names appearing in 3 stepped batches identical to the opener; 1700~2100ms values and Swing bar fill smoothly emerging): Data Panel executes a fresh jelly spring expansion starting from horizontal 10% & vertical 50% (startCX 1/10 of the canvas) growing directly to the left target position (targetXRatio 0.018, size 54% × 93%) with Hermite damped oscillation without lingering in the center, while radar and swing hide all metrics and values; after Data Panel settles, radar and swing enter from below the vertical center growing size from 0 to target with no labels or values shown; once in place, metric names grow upward in three stepped batches separated by 0.1s (Rating/KPR → Multi-Kill/Surviving → KAST/ADR/Round Swing) with Chinese alias tags underneath identical to the opener; finally values and Swing bar fill smoothly emerge and expand to player values. During layout authoring (non-playback editing mode), elements render in real-time at their configured positions (`isEditing: !playing`) without requiring page refresh.
- Showcase title and subtitle support customizable font size (`titleFontSize` / `subtitleFontSize`) and font color (`titleColor` / `subtitleColor`). Subtitle defaults to rank (e.g. `#1`, `#2`) rather than "n 场综合数据", while the map count is displayed in the bottom-right interior of the Data Panel as "地图数: n". Subtitle provides four glowing color presets (gold `#ffd700`, silver `#e2e8f0`, bronze `#cd7f32`, white `#f4f6f8`), each with outer glow effect, alongside bold and italic options (`subtitleBold` / `subtitleItalic`). Selection bounding boxes for title, subtitle, and player image measure the actual rendered content dimensions dynamically rather than using fixed width estimates, matching content bounds snugly.
- Player slides support team logo uploading, dragging, and transform scaling (`teamLogoUrl` / `teamLogoTransform` / `teamLogoX/Y/Scale`), rendered exactly once by the `teamLogo` layer with proportional contain scaling and layer ordering. Never draw an additional large background copy of the same asset (the former 30% background watermark was removed because the same image appeared twice). The layer logo follows the arrival rhythm (`arrivalTeamLogoAlpha`: hidden until `FIRST_PLAYER_TITLE_START_MS` = 1100ms, then a 500ms cubic fade-in; forced to 1 in editing mode so authoring never hides it) and is multiplied by the 500ms `exitFadeOutOpacity` exit fade — a player leaving into a BEST MVP or a cross-team slide must fade its team logo, background image and background scrim together with the rest of its canvas elements. Every draft's layer list must contain the `teamLogo` layer (new drafts include it; `stripLegacyDraftFields` migrates legacy lists, and the renderer normalizes the list before painting), and uploading a logo patches the previewed slide atomically so it appears on the canvas immediately without a page reload. The drawn logo box comes only from `showcaseTeamLogoSize` (`min(frameWidth, frameHeight) × 0.14 × scale`, contain fit); the preview's selection outline and hit test must call the same helper, never a separately invented ratio, or the dashed box drifts off the pixels. Team-logo scale is intentionally uncapped on the upper end (`SHOWCASE_TEAM_LOGO_SCALE_MIN` = 20 is the only limit; the inspector exposes a free number field, not a bounded slider) — when the logo grows past the frame only its center is kept within 0–100%, while the player image keeps its own 30–250 cap. Its center may be dragged anywhere inside the canvas (0–100% on both axes) just like the player image; never clamp the player image or team logo by their own footprint (`targetBaseBounds`) — that turns the intended edge of the canvas into an invisible wall the pointer hits long before the frame.
- **Single Source of Truth Transform Resolution for Canvas Elements**: To prevent desynchronization between selection bounds, hit testing, inspector inputs, and the canvas renderer, every canvas element must adhere to a single-source-of-truth resolver function:
  - `image`: `resolveImageTransform(layout)` (position and scale both come from the layout and apply to every player). `stripLegacyDraftFields` migrates the active legacy slide transform into `layout.imageX/imageY/imageScale`, then removes every per-slide `imageTransform`.
  - `teamLogo`: `resolveTeamLogoTransform(layout, slide)` (position per slide with layout fallback, scale unified through single resolver). `ShowcaseEditor` inspector inputs and `ShowcasePreview` drag callbacks must read from these resolvers and perform one functional `setDraft` update that changes only the owning state (layout only for image; slide and layout together for team logo), never splitting updates across separate `patchSlideAt` and `setDraft` calls which causes React state overwrite races. All new elements added in the future must introduce a dedicated `resolve<Element>Transform` resolver and share the exact same bounding measurement between renderer and selection outline.
- **Every canvas element is a reorderable layer.** `ShowcaseLayoutDraft.layers` is a top-first list consumed by `normalizeShowcaseLayers`/`showcasePaintOrder`: `watermark` (Rating 3.0 caption), `radar`, `swing`, `image`, `teamLogo`, `subtitle`, `title`, `panel` (Data Panel), `particles`, `background` (background image **plus** its 46% scrim). Default order is `watermark, radar, swing, image, teamLogo, subtitle, title, panel, particles, background` (no `swing`/`watermark` for Rating 2.0); `showcaseDefaultLayers(ratingVersion)` is the only default source. The inspector renders every row with labels from `SHOWCASE_LAYER_LABELS`, drag/up/down reorder, and persists the normalized list. Legacy `name` rows are split into `subtitle` + `title` (subtitle still paints above title); `normalizeShowcaseLayers` also inserts any missing layer at its default relative position and drops unknown/duplicate keys, so old drafts gain the background/panel/particles/watermark rows automatically. Intro stages and the BEST entrance paint the same ordered stack (matchInfo/entrance only need background + particles), while the opaque accent gradient base, the BEST spotlight handoff, and the black fade-in overlay stay outside the stack. Never paint background, Data Panel, particles or the watermark before/after the layer loop again — they must all go through the one ordered pipeline so preview and export stay identical.
- In the library (`LibraryView`), users can multi-select players to group into a team (`PlayerTeam`: id, name, logoUrl, playerSteamIds), with customizable team name and logo. Teams can be added to the showcase as an entire unit. Clicking "全部选手一键加入轮播" sorts the queue grouped by team (team members clustered together first, ungrouped players following), automatically injecting the team logo into each member's showcase slide. Only normal subsequent player-to-player transitions interpolate vertices directly.
- The base outer radar ring is persistent and never fades; only its separate highlight fades in and out. During the opener, metric labels stay at their default locations. Metric names and the Swing track/endpoint labels remain visible once shown; numeric labels count continuously from outer reference to average, fade out at the third-to-fourth boundary, then reappear while counting from zero to player values. Both the red average radar baseline and the red Round Swing reference line remain fixed and visible while the player data expands. Entering stage 3 (average), the outer-ring highlight fade-out, metric numeric label roll/interpolation (reference to average) & color transition to red, average radar polygon fade-in, and Round Swing line/title/value fade-ins all complete within the first 0.3s (300ms, `SHOWCASE_INTRO_AVERAGE_TRANSITION_MS`); Round Swing values must fadeIn smoothly rather than popping in abruptly. Only normal player-to-player transitions interpolate the six radar vertices directly.
- Background-music volume is one draft-level percentage (`audioVolume`, default 100) shared by preview and export. The playback control must not declare `min`/`max` or clamp the value: any finite number (negative, above 100, arbitrarily large) is valid. Preview applies it through a Web Audio `GainNode` via `showcaseAudioGain(percent) = percent / 100` (because `HTMLAudioElement.volume` only accepts 0–1), and export forwards the same number as the final `BeginVideoExport` argument so FFmpeg applies a `volume=<percent/100>` filter before its delay/trim chain; the backend rejects only non-finite values (`invalid_showcase_video`) and never imposes a numeric range. Both export paths (worker and main-thread fallback) must pass the volume.
- BEST remains strict per-metric first place. When its optional entrance is enabled, every BEST player (including the first) adds a 3-second player-name entrance followed by a 1-second crossfade into the main scene; this timing is part of preview, timeline, and export duration. When transitioning to a player with a BEST MVP entrance or when switching across different teams, the preceding player's canvas elements execute a smooth 500ms FadeOut exit. In the MVP spotlight scene, the left and right side-name text streams continue scrolling endlessly throughout the scene without stopping at the end; the lower-right main title glides in from off-canvas to settle at 3/4 width (0.75x) within the first 35% of the entrance, and subsequently drifts continuously to the left at a gentle pace. During the 1-second handoff the entrance must not freeze: `bestEntranceHandoffProgress` continues the progress past 1 at the entrance's own speed (1000/3000 of a unit) so both side-name streams and the main title keep moving while the whole spotlight layer fades out via `1 - handoffProgress`. The main player scene (Data Panel, radar, Round Swing, player image, title/subtitle, team logo) stays fully hidden during entrance and handoff (`sceneOpacity` = 0 in handoff, `dataPanelOpacity` = 0) — never cross-fade a static player frame under the handoff, because it would flash for a frame and then be replayed by the arrival pipeline. Following the MVP entrance (or on cross-team player transitions), the canvas elements execute the full arrival pipeline to present the player; normal intra-team player transitions without BEST continue to interpolate radar vertices directly with polygon morphing and crossfade.

## UI style conventions

These rules govern the application chrome and component aesthetics. They must be preserved in every style change, component addition, or refactor.

### Design tokens
- `--transition-fast` (150ms), `--transition-base` (200ms), `--transition-slow` (300ms) — all use `cubic-bezier(0.4, 0, 0.2, 1)`. Never use raw duration values or other easing functions.
- `--hover-bg: rgba(255,255,255,0.04)` / `--hover-bg-strong: rgba(255,255,255,0.07)` — the only hover background values. Never use hardcoded hover opacity.
- `--shadow-sm: 0 2px 8px rgba(0,0,0,0.2)` / `--shadow-md: 0 8px 30px rgba(0,0,0,0.24)` — shadow elevation scale. The existing `--shadow` is for large modal/canvas use only.
- Keep the existing color palette (`--bg` through `--focus`). Extended surface and glow tokens: `--surface-0` (`var(--bg)`), `--surface-1` (`var(--sidebar)`), `--cyan-dim`, `--cyan-glow`, `--gold`, `--gold-dim`, `--gold-glow`, `--danger-dim`, `--success-dim` provide semantic depth layers and subtle accent glows without introducing external color dependencies.

### Component interaction patterns
- Every interactive element (button, card, list item, input, tab, chip) must have a `transition` that includes at least `background` and `border-color` using `var(--transition-fast)`.
- Buttons: `will-change: transform` set; `:active` must apply `scale(0.98)` for press feedback. Never use `translateY(1px)` as a press effect.
- Cards and bordered panels: hover must brighten the border (`--border-strong` from `--border`). Never lift, scale, or add drop-shadow on card hover.
- Inputs and search boxes: `:focus` must add `box-shadow: 0 0 0 3px rgba(117, 167, 255, 0.12)` with `border-color: var(--focus)`. Input `:hover` must brighten border.
- Segmented controls, tabs, and view-switch buttons: every child button must have `transition` on `background` and `color`. Active state must use a distinct background fill.

### Sidebar navigation
- Active nav item must use `box-shadow: inset 3px 0 0 #838c97` for the left accent bar.
- Each nav button must have a `::before` pseudo-element (2px wide, 18px tall, `#838c97`) that animates from `scaleY(0)` to `scaleY(1)` on active state — this is the animated indicator. Do not use only the `box-shadow` inset bar without the `::before` element.

### Micro-animations
- `@keyframes selection-in`: opacity 0→1, translateY(-2px)→none, 0.2s ease-out — used on `.selection-bar`.
- `@keyframes panel-in`: opacity 0→1, translateY(8px)→none, 0.25s ease-out — used on sticky bottom panels.
- `@keyframes backdrop-in`: opacity 0→1, 0.15s ease-out — used on modal backdrops.
- `@keyframes dialog-in`: opacity 0→1, translateY(5px) scale(0.99)→none, 0.2s ease-out — used on modal dialogs.
- `@keyframes page-in`: opacity 0→1, translateY(4px)→none, 0.2s ease — used on `.page` wrapper.
- Do not remove or replace these keyframes. Add new animations only when a component has no existing animation match.
- `prefers-reduced-motion` and `.reduce-motion` must zero out all animation/transition durations (0.001ms). Every new animation must be covered by these overrides.

### Layout spacing
- Page padding: 27px 30px 30px (responsive: 22px 20px at ≤1280px).
- `.page-header` margin-bottom: 26px. Never shrink this below 22px.
- Minimum viewport: 1180×720. Default: 1440×900. Do not add mobile breakpoints.
- Cards use `--radius: 10px` for outer radius, 7–8px for nested elements. Do not use radius values outside this range.
- Consistent gap scale: 4, 8, 12, 16, 24, 32px. Do not use gap values outside this scale.

### Styling approach
- Keep using CSS custom properties in `:root` as the single source of truth. No Sass/Less variables.
- No CSS modules or CSS-in-JS — the project uses a single `styles.css` with feature-specific overrides in `media.css` and `metadata.css`.
- Hardcoded color values in TSX component files (e.g. RadarCanvas.tsx) are acceptable for canvas-rendered artwork; do not use hardcoded colors in DOM React components — use CSS variables instead.
- Never add emoji icons, decorative looping motion, or hover-only affordances. All interactive elements must have `:focus-visible` outline.
- Never use browser-native dialogs (`window.alert/confirm/prompt`) anywhere under `frontend/src`: they are unstyled OS widgets that break UI consistency. Use the app's own dialog host instead — `useAppStore.showConfirm(options)` / `showPrompt(options)` (promise-based, `components/ui/AppDialog.tsx`, mounted once in `App.tsx`), which renders with the shared `backdrop-in`/`dialog-in` animations, CSS-variable tokens, Enter=confirm/Escape=cancel, and focus handling.

## Frontend architecture

- Routing: React Router. `App.tsx` is a shell with lazy routes and button-based sidebar nav (never `NavLink` — the CSS targets `.sidebar nav button`). View state lives in zustand stores (`stores/appStore.ts`, `stores/studioStore.ts`); views read state from stores instead of props drilling.
- `StudioView` is a shell; editors live in `RadarEditor.tsx`, `OverlayEditor.tsx`, `ShowcaseEditor.tsx`, `ShowcasePreview.tsx`. Shared logic: `useDraft.ts` (save debounce hook), `showcaseMath.ts` (pure/timeline functions — importable from tests), `showcaseRender.ts` (canvas rendering). `SaveState` is defined once in `components/ui/SaveStatus.tsx` and re-exported through the `components/ui/index.ts` barrel.
- Shared components live in `components/` (`demo/DemoCard.tsx` with `variant="catalog" | "analysis"`, `ui/` primitives). Formatting helpers live in `lib/format.ts` (`formatDemoDate`, `formatValue`, `signed`, `errorMessage`) — views must not re-define them.
- Video export rendering runs in a Web Worker (`showcaseExportWorker.ts`) using `OffscreenCanvas` when `Worker` and `OffscreenCanvas` exist; frames upload via `bridge.appendVideoFramesBinary` (see the desktop shell & embedded server section). The main-thread `toDataURL` + `appendVideoFrames` loop stays as the fallback.
- Shared render code must be Worker-safe: create canvases through `createCanvas`, obtain 2D contexts via `canvas2D`, read image dimensions through `imageWidth`/`imageHeight` (works for `HTMLImageElement` and `ImageBitmap`), load fonts in a worker via `FontFace` + `globalThis.fonts` — never call `document.*` directly.
- All canvas fonts are self-hosted in `frontend/public/fonts/` (`NotoSansSC-Variable.ttf`, `Bangers-Regular.ttf`, `BlackOpsOne-Regular.ttf`, `PlayfairDisplay-Italic-VF.ttf`) with their OFL licenses and declared as `@font-face` in `styles.css`; the runtime must never request a font from a CDN. `PlayfairDisplay-Italic-VF.ttf` is the `BEST` display font (`italic 900`). The showcase preview/export path validates it in `ensureShowcaseFonts` (worker `FontFace` descriptors and DOM `document.fonts.load` must both say `italic 900`), and `App.tsx` pre-warms it once for the library/overlay radars, which never run that validation.
- Every design-space pixel value in the 1920×1080 showcase (title, subtitle and their glow radii, metric labels, watermark) must be multiplied by `fontScale = backingWidth / SHOWCASE_EXPORT_WIDTH`; `showcaseTitleTextStyle`/`showcaseSubtitleTextStyle` are the only source for title/subtitle font size, and both the renderer and the selection-box measurement must use them.
- The player image has one global transform: `imageX/imageY/imageScale` live only on the layout (scale percent, 30–250) and are shared by every player. `resolveImageTransform`/`showcaseImageBox` are the only readers; the editor's X/Y inputs and the selection box must show exactly what the renderer draws, and single-axis edits carry the other axis over instead of writing 0. Dragging (`clampShowcaseTransform`) bounds the image and team-logo **center** only to 0–100% on each axis so they can be pushed against the canvas edges (the part outside the frame is simply clipped at paint time); only `radar`/`swing` keep footprint-based clamping and `title`/`subtitle` keep 2–98%. While the pointer is down the renderer takes the live image transform through `effectiveLayout` and the live team-logo transform through `animations.pendingTeamLogoTransform` (never rebuild the `slides` array per frame — that invalidates `ratedDerivationCache` and makes the drag lag), and `ShowcasePreview.onTransformPreview` feeds the same values to the inspector so its X/Y/scale fields track the drag in real time; the draft is only written on pointer-up. On pointer-up, a committed drag must retain its `pendingTransform` until the rendering effect runs with the updated draft props; never clear it and redraw the old draft synchronously, which produces a one-frame rebound. Every future draggable element must use this shared committed-drag lifecycle rather than target-specific cleanup.
- `RadarCanvas` is wrapped in `React.memo`; `geometry`/`labelBounds` in `RadarCanvas.tsx` are cached by a `compact|showSwing|width|height` key (these are constant across export frames).

- In the library (`LibraryView`), "制作雷达/加入叠图/加入轮播/全部加入轮播" only save the draft, set the studio seed (`useStudioStore.setSeed`), and show a toast — they must never navigate to the studio route. "全部加入轮播" includes every saved player with match stats in the current player sort order, updates existing slides by SteamID, and reports any individual failures without discarding successful additions.
- Right-clicking a player in the library player list opens a `context-menu` with "取消关注/关注", "刷新头像" (calls `RefreshPlayerAvatars`, which bypasses the fallback TTL and refetches immediately, then applies the result through `applyAvatar` from `PlayerAvatar.tsx`), "修改名称" (prompts for a new display name and calls the `RenamePlayer` bridge method, which updates `players.latest_name` plus the `followed_players`/`discovered_players` copies; demo dedupe keys are name-independent because `HistoryService.BuildPlayerSetHash` hashes SteamIDs only), and "删除资历" (deletes that player's match stats). Keep this affordance; do not remove it during refactors. The library header also has a "清洗战队前缀" button (bridge `CleanTeamPrefixNames`) that re-parses at most the 3 most recent demos of each affected player to determine team prefixes, renames what it can, and returns per-player `TeamPrefixCleanResult` entries (`renamed`/`skipped`/`failed` + reason) that the UI summarizes in a toast plus an error list of why some were skipped.

Every avatar fetch/download failure is logged with its reason (HTTP status or exception) to `~/.csplayerstatsradar/logs/avatars.log` — keep this logging when refactoring `SteamAvatars`; it is the primary way to diagnose Windows fetch failures. The showcase slide image defaults to the player avatar (`item.imageUrl ?? item.avatarUrl`); `ShowcaseEditor` backfills `avatarUrl` for any slide missing it on load.

  - `DemoData` (Radar.Domain) is still the app-wide model.   - `Kills.TradedPlayerSteamID` is re-derived in the Mapper with the old rule (≤5·64-tick look-back, previous cross-side victim id) — keep it so trade credit in KAST/per-round analysis still works.
  - 完美平台 demos prefix player names with 「战队名 玩家名」, and the demo carries no real team-name field (`PlayerInfo.Csda.Team` is only csda's synthetic "Team A"/"Team B" side label — never use it to strip). `MatchDataMapper.Map(match, teamTags)` therefore strips a team prefix only when (a) at least two players in the same demo share that same 1–3-word prefix (`TeamPrefix.ClusterPrefixes`, case-insensitive word-level cluster) or (b) the prefix is listed in the Settings `team_tags` list (comma-separated, case-insensitive, entries may themselves contain spaces and are matched as a whole prefix, persisted via `AppConfig.TeamTags` and `ConfigManager.WhitelistedKeys`). The longest matching prefix wins, at most 3 words are stripped, and stripping is skipped whenever the remainder would be empty.
